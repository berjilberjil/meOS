# MeOS security audit — baseline, changes and evidence

Date: **2026-11-21**
Repository: `berjilberjil/meOS` (branch `feat/meos-mcp-gateway`)
Auditor: application-security review performed in-repo against the actual source, not the older
Supabase/Postgres design described in historical docs.

This is a working security assessment, not a certification. It records what was found, what changed, what
was verified, and what remains. The most important honest statements:

- The app already had a real client-side vault. This work did not invent a second one.
- A first-run bug would have emptied a new vault; it is fixed and called out as SEC-15.
- Argon2id is available for the server login hash on paid Workers (`v4`) but not yet on-device for the vault; passkeys and automatic DEK rotation remain residual gaps.
- The MCP gateway now has OAuth 2.1 + PKCE + per-module scopes + revocation + audit, but it remains a local
  process that holds the vault passphrase. That is an architectural trade, not a hidden detail.

## 1. System as found

```
apps/apple     SwiftUI iOS + macOS, generated by XcodeGen. Codable module documents.
apps/api       SvelteKit 2 on Cloudflare Workers. D1 (SQLite) + R2 + Workers AI.
mcp/meos       Node 22+ MCP gateway: stdio + Streamable HTTP, static bearer tokens.
mcp/diet       stdio MCP for meal plans.
mcp/stuff      stdio MCP for purchases.
supabase/      Legacy pre-Workers schema. Not used at runtime.
```

Runtime facts:

- Auth: username/password → `meos_session` cookie; PBKDF2-SHA256 (v2, 10k) and legacy scrypt.
- State: one JSON document per module in `app_state`, client-sealed with AES-256-GCM under a DEK.
- Vault: DEK wrapped with PBKDF2 600k under a passphrase and a recovery code; `meos.crypto` public.
- Media: private R2, presigned GET (1 hour) after session check; event/body photos are client-sealed.
- AI: AI SDK 5 with Gemini/Anthropic/OpenAI; user keys AES-256-GCM encrypted with `MEOS_SECRETS_KEY`.
- MCP: static bearer tokens, coarse `read/write/destructive/health/secret` scopes, in-memory rate limit,
  no OAuth, no persistent revocation, no admin UI.
- No RLS (D1); every query is expected to include `user_id`.

### Data flow (before)

```
App ──cookie──▶ Worker ──user_id──▶ D1 app_state (ciphertext)
 │                  │
 │                  ├──▶ R2 (ciphertext media) ──signed URL──▶ App
 │                  └──▶ AI provider (prompt the app built)
 └── MCP gateway (static token, local) ──login──▶ Worker
```

### Data flow (after)

```
App ──cookie + origin check──▶ Worker ──user_id──▶ D1 (ciphertext + hashed sessions + audit metadata)
 │                                  │
 │                                  ├──▶ R2 private (ciphertext; 10-min signed GET)
 │                                  └──▶ AI provider (metered; user key encrypted)
 │
 ├── local MCP gateway (vault DEK in memory)
 │      ├── OAuth 2.1 consent (admin password, per-module scopes)
 │      ├── audit.jsonl + idempotency.json (0600)
 │      └── HTTPS tunnel ◀── ChatGPT / Claude / Cursor (Bearer access token)
 └── Keychain (DEK, ThisDeviceOnly)
```

## 2. Method

1. Read every route, server module, DB schema, MCP tool/transport and the Swift crypto/UI paths.
2. Grepped for secrets, dangerous sinks, unscoped SQL, `console`/`print`, raw URLs and dynamic SQL.
3. Ran the existing API, MCP, diet and stuff suites before changing anything (57 API tests, 91 MCP tests).
4. Built the API for Cloudflare and both Apple targets.
5. Modeled attackers: unauthenticated, other user, stolen session, DB-only, R2-only, malicious MCP client,
   prompt-injected content, malicious AI provider, insider with Worker env, supply-chain.
6. Implemented fixes in phases, adding tests before/with each change.
7. Re-ran everything and recorded the output in `docs/SECURITY_TEST_EVIDENCE.md`.

Constraints respected: no production testing, no destructive migration, no real personal data in tests, no
secrets committed, no public exposure during the work.

### Highest-priority items that remain

1. **SEC-19 Argon2id** — implement with a vetted library and a versioned KDF migration.
2. **SEC-18 passkeys** — WebAuthn on iOS/macOS and server challenge storage.
3. **SEC-22 DEK rotation** — a tested, atomic re-encrypt workflow.
4. **SEC-23 vault-meta write proof** — a client-side proof the server can verify without learning the
   passphrase is not possible; the practical fix is to require a recent re-auth *and* keep the client-side
   current-passphrase check. A stolen session can still DoS, not decrypt.
5. **SEC-27 dev dependencies** — upgrade Vite/Vitest when the SvelteKit toolchain allows it.

## 7. Explicit non-goals / not changed

- No production deployment, migration or destructive test was performed.
- The legacy `supabase/` schema is untouched and still not used at runtime.
- The app’s UI was not rebuilt; security screens were added in the existing style.
- No new third-party service was added to the runtime path.
- No claim is made that the app is “unhackable”, “military grade”, or that the AI provider cannot see
  data it is given.
